# ASVS checks

ASVS version 5.0.0. Selection size: 93 requirements. Source: OWASP Application Security Verification Standard, https://github.com/OWASP/ASVS, licensed CC BY-SA 4.0. This file adds search hints and evidence rules to a subset of the requirements. Requirement text is quoted verbatim from the release; do not reword it.

Each entry has four fields. **Requirement** is the official text. **Where to look** lists search strategies; run them in the target repository. **Implemented when** and **Not implemented when** state what you must observe for each status. Cite `path:line` or a config key for every `implemented` status. If a framework default is the evidence, cite the config file and key, or the middleware or package entry that enables it.

Framework defaults change between versions. Read the installed version from the lock file before relying on a default, and cite the lock file line.

Two kinds of requirement. Sink-type (injection, traversal, SSRF, open redirect, executing uploads, deserialisation): any confirmed unsafe site receiving untrusted input is `not implemented`, however many safe sites exist; `partial` only when the control is present and no unsafe site is confirmed. Coverage-type (cookie attributes, CSRF on forms, validation on handlers, security headers, CSP directives, logging of events): `not implemented` when the control is absent or the primary instance is wrong (the session cookie, login and state-changing forms, the CSP minimum directives object-src and base-uri, authentication events); `partial` when the primary instance is correct and secondary instances are missing.

The entry header gives the ASVS level and the applicability. `core` entries apply to every web application. `conditional: <key>` entries apply only when the condition holds; the detection rules for each key are in `reference/detection.md`. If the condition does not hold, the status is `n/a`.

## V1 Encoding and Sanitization

### V1.2.1 (Level 1, core)
**Requirement:** Verify that output encoding for an HTTP response, HTML document, or XML document is relevant for the context required, such as encoding the relevant characters for HTML elements, HTML attributes, HTML comments, CSS, or HTTP header fields, to avoid changing the message or document structure.
**Where to look:** Find every place HTML is produced: template files (`*.blade.php`, `*.twig`, `*.html.j2`, `*.html`, `*.ejs`, `*.pug`, `*.hbs`, `*.jsx`, `*.tsx`, `*.vue`), and code that builds markup by string. Search for escape-bypass markers: Blade `{!! ... !!}`, Twig `|raw` and `autoescape false`, Jinja2 `|safe` and `Markup(`, Django `mark_safe` and `{% autoescape off %}`, PHP `echo $` without `htmlspecialchars(`, EJS `<%- `, Handlebars `{{{ `, React `dangerouslySetInnerHTML`, Vue `v-html`, JS `innerHTML`, `outerHTML`, `document.write`, `insertAdjacentHTML`. Check header and cookie output too: `header(` in PHP, `res.setHeader`, `res.redirect` with user data, Django `HttpResponse(` with f-strings. Confirm the template engine autoescapes by default (Blade `{{ }}`, Twig, Jinja2 in Flask, Django templates, React JSX).
**Implemented when:** The project uses an autoescaping template engine or UI framework and every bypass marker found outputs only constants or data already passed through a sanitizer (cite the template path:line and the engine default, for example `resources/views/` using Blade `{{ }}`). Header values never contain raw request data.
**Not implemented when:** A confirmed sink outputs untrusted data into HTML, attributes, CSS or headers without context-appropriate encoding: string concatenation or `echo`/`print` of request or database data without `htmlspecialchars`, `escape()` or an autoescaping engine, or a bypass marker (`{!! !!}`, `|raw`, `|safe`, `mark_safe`, `v-html`, `dangerouslySetInnerHTML`, `innerHTML`) receiving user-controlled data. A confirmed unsafe sink receiving untrusted input is `not implemented`, however many safe sites exist. Use `partial` only when the control exists but is applied incompletely and no unsafe site is confirmed (bypass markers exist but every one receives constants or sanitized data that you could not fully trace).

### V1.2.3 (Level 1, core)
**Requirement:** Verify that output encoding or escaping is used when dynamically building JavaScript content (including JSON), to avoid changing the message or document structure (to avoid JavaScript and JSON injection).
**Where to look:** Search where server data is written into script context: inline `<script>` blocks in templates, `window.__DATA__ =` or `var x = ` assignments with template tags, `JSON.parse('` with interpolation, `on*=` handler attributes with template tags, and `eval`/`new Function` fed with data. Look for the safe helpers: PHP `json_encode(` with `JSON_HEX_TAG|JSON_HEX_AMP|JSON_HEX_APOS|JSON_HEX_QUOT`, Laravel `@json(`, `Js::from(`, Twig `|json_encode|raw` and `|escape('js')`, Jinja2 `|tojson`, Django `json_script` and `|escapejs`, Node `serialize-javascript`, `JSON.stringify` followed by `.replace(/</g, '\\u003c')`. Also check JSONP endpoints (`callback=` parameter).
**Implemented when:** Every server value placed in a script block or inline handler goes through a context-aware helper (`@json`, `Js::from`, `|tojson`, `json_script`, `escapejs`, `serialize-javascript`) or is delivered as a separate JSON response or `data-` attribute that is HTML-escaped. Cite the file:line of the helper call.
**Not implemented when:** Data is concatenated into `<script>` content or handler attributes with plain HTML escaping only or none (`var user = '<?= $name ?>'`, `const d = {{ data|safe }}`), `JSON.stringify` output is embedded without escaping `<`, or a JSONP callback name is echoed unvalidated. A confirmed unsafe sink receiving untrusted input is `not implemented`, however many safe sites exist. Use `partial` only when the control exists but is applied incompletely and no unsafe site is confirmed (script-context sites exist and you found a safe helper on some but could not trace the rest).

### V1.2.4 (Level 1, core)
**Requirement:** Verify that data selection or database queries (e.g., SQL, HQL, NoSQL, Cypher) use parameterized queries, ORMs, entity frameworks, or are otherwise protected from SQL Injection and other database injection attacks. This is also relevant when writing stored procedures.
**Where to look:** Find all database access: ORM models, query builders, repositories and raw SQL files. Search for raw or concatenated queries: PHP `DB::raw`, `DB::select(` with variables in the string, `whereRaw`, `orderByRaw`, `selectRaw`, `->query(` with `.` or `"$var"`, `mysqli_query(`, `->prepare(` without bound values, Doctrine `createQuery(` or `executeQuery(` with concatenation; Node `knex.raw`, `sequelize.query(` with template literals, `.query(` with backticks or `+`, Prisma `$queryRawUnsafe`, `$executeRawUnsafe`, Mongo `$where` and filters built from `req.body` objects without type checks; Python `cursor.execute(f"`, `execute("..." % `, `.format(` in SQL strings, Django `.raw(`, `.extra(`, `RawSQL(`, SQLAlchemy `text(f"`. Check stored procedure definitions and migrations for dynamic SQL (`EXECUTE`, `sp_executesql`, `CONCAT` into statements). Check identifiers (column and table names, `ORDER BY`) taken from requests against an allowlist.
**Implemented when:** All queries go through an ORM or query builder with bound parameters, or raw queries use placeholders with a separate bindings argument (`?`, `:name`, `%s` with a params tuple, `$1`). Raw sites that remain take no user data or only allowlisted identifiers. Cite the data-access layer path:line and one raw example if present.
**Not implemented when:** A confirmed query string is built from request, header, file or other untrusted data by concatenation, interpolation or `format`. List each as path:line. A confirmed unsafe sink receiving untrusted input is `not implemented`, however many safe sites exist. Use `partial` only when the control exists but is applied incompletely and no unsafe site is confirmed (raw queries exist but their inputs are constants or validated values).

### V1.2.5 (Level 1, core)
**Requirement:** Verify that the application protects against OS command injection and that operating system calls use parameterized OS queries or use contextual command line output encoding.
**Where to look:** Search for process execution: PHP `exec(`, `shell_exec(`, `system(`, `passthru(`, `proc_open(`, `popen(`, backticks, Symfony `Process::fromShellCommandline`; Node `child_process`, `exec(`, `execSync(`, `spawn(` with `shell: true`; Python `os.system(`, `os.popen(`, `subprocess` with `shell=True`, `commands.getoutput`. Also search wrappers around `ffmpeg`, `convert`/ImageMagick, `git`, `pdftk`, `wkhtmltopdf`, `tar`, `ping`. For each hit trace whether any argument comes from request data, uploaded filenames, or database content.
**Implemented when:** No process execution calls exist (cite the search performed: patterns grepped, directories covered, 0 hits), or every call passes arguments as an array without a shell (`spawn(cmd, [args])`, `subprocess.run([...])` with `shell=False`, Symfony `new Process([...])`) and user values are validated against an allowlist or escaped with `escapeshellarg`/`shlex.quote`. Cite the call site path:line.
**Not implemented when:** A shell string is built from untrusted data (`exec("convert " . $file)`, `exec("ls " + dir)`, `os.system(f"...")`, `shell=True` with variables) with no `escapeshellarg`, `shlex.quote` or allowlist. A confirmed unsafe sink receiving untrusted input is `not implemented`, however many safe sites exist. Use `partial` only when the control exists but is applied incompletely and no unsafe site is confirmed (process calls exist and take only constants or allowlisted values, but the allowlist is incomplete).

### V1.3.1 (Level 1, conditional: rich-text)
**Requirement:** Verify that all untrusted HTML input from WYSIWYG editors or similar is sanitized using a well-known and secure HTML sanitization library or framework feature.
**Where to look:** Applies only if users submit HTML (WYSIWYG editors such as TinyMCE, CKEditor, Quill, Trix, TipTap; markdown rendered to HTML). Search for these libraries in `package.json`, `composer.json`, `requirements.txt` and templates, then follow the submitted field to the save handler and to the render step. Look for sanitizers: PHP `HTMLPurifier`, `mews/purifier`, Symfony `HtmlSanitizer`; Node `DOMPurify` (with jsdom), `sanitize-html`, `xss`; Python `bleach`, `nh3`, `django-bleach`. Look for unsafe renders: `{!! $post->body !!}`, `|safe`, `v-html`, `dangerouslySetInnerHTML`, markdown libraries with `html: true` or `unsafe` options.
**Implemented when:** Rich HTML is passed through a maintained sanitizer with an allowlist configuration on the server before storing or before rendering. Cite the sanitizer call path:line and its config.
**Not implemented when:** Rich HTML is stored or rendered raw, sanitized only by regex or `strip_tags`, or sanitized only in the browser. A confirmed unsafe site is `not implemented`, even if other sites are safe.

### V1.3.2 (Level 1, core)
**Requirement:** Verify that the application avoids the use of eval() or other dynamic code execution features such as Spring Expression Language (SpEL). Where there is no alternative, any user input being included must be sanitized before being executed.
**Where to look:** Search for dynamic code execution: PHP `eval(`, `assert(` with strings, `create_function`, `preg_replace` with `/e`, `include`/`require` of variable paths, `call_user_func` with request-controlled names, Node `eval(`, `new Function(`, `vm.runInContext`, `vm.runInNewContext`, `setTimeout("string"`, `require(` with variable paths; Python `eval(`, `exec(`, `compile(`, `__import__(` with variable names, template strings rendered from user input (`render_template_string(` with user data, `Template(user_input)`, Twig `createTemplate`). Also search expression engines and ORMs that accept expressions (`$where`, formula fields).
**Implemented when:** None of these calls exist, or every hit takes only constants or developer-controlled data. Cite the search performed (patterns and directories, with hit count) and, for each remaining hit, path:line with the reason it is safe.
**Not implemented when:** A dynamic execution call receives request, file or database content without allowlisting (`eval($_GET['x'])`, `render_template_string(request.args['t'])`, `require(userPath)`).

### V1.3.6 (Level 2, conditional: outbound-urls)
**Requirement:** Verify that the application protects against Server-side Request Forgery (SSRF) attacks, by validating untrusted data against an allowlist of protocols, domains, paths and ports and sanitizing potentially dangerous characters before using the data to call another service.
**Where to look:** Applies only if server code requests URLs that a user can influence (webhooks, link previews, URL import, image fetch by URL, PDF from URL, OAuth discovery, RSS). Search for HTTP clients: PHP `curl_init`, `file_get_contents('http`, Guzzle `Http::get`, Laravel `Http::`, Symfony `HttpClient`; Node `fetch(`, `axios`, `got`, `node-fetch`, `http.request`, `undici`; Python `requests.get(`, `httpx`, `urllib.request.urlopen`, `aiohttp`. Trace the URL argument back to request data or stored user data. Look for allowlist code: host comparison, scheme check (`http`/`https` only), port check, resolution to IP with blocking of private ranges (`127.0.0.0/8`, `10.0.0.0/8`, `169.254.169.254`), redirect following disabled (`allow_redirects=False`, `maxRedirects: 0`, `CURLOPT_FOLLOWLOCATION` false).
**Implemented when:** User-influenced URLs are checked against an allowlist of schemes, hosts, ports and paths before the request, and redirects are not followed blindly. Cite the validation function path:line.
**Not implemented when:** A user-supplied URL is fetched with no allowlist, or only a string-prefix or blocklist check that can be bypassed (redirects, DNS rebinding, alternate IP notation). A confirmed unsafe site is `not implemented`, even if other sites are safe.

### V1.3.11 (Level 2, conditional: mail)
**Requirement:** Verify that the application sanitizes user input before passing to mail systems to protect against SMTP or IMAP injection.
**Where to look:** Applies only if the app sends or reads mail with user-influenced values (contact forms, invites, password reset, notifications). Search mail code: PHP `mail(` with user headers, Laravel `Mail::`, Symfony Mailer, PHPMailer; Node `nodemailer`, `sendgrid`, `imap`; Python `smtplib`, `email.message`, Django `send_mail`, `EmailMessage`, `imaplib`. Check where `To`, `From`, `Cc`, `Bcc`, `Subject` and `Reply-To` come from. Look for CR/LF stripping (`\r`, `\n` checks, `FILTER_VALIDATE_EMAIL`, framework address objects) and for header values built by string concatenation.
**Implemented when:** User values reach headers only through the mail library's address and subject APIs (which reject newlines) or after explicit CR/LF rejection and address validation. Cite the mail-sending path:line.
**Not implemented when:** User input is concatenated into raw headers or the `additional_headers` argument of `mail(`, or `To`/`Subject` take unvalidated values containing newlines.

### V1.5.1 (Level 1, conditional: xml)
**Requirement:** Verify that the application configures XML parsers to use a restrictive configuration and that unsafe features such as resolving external entities are disabled to prevent XML eXternal Entity (XXE) attacks.
**Where to look:** Applies only if the app parses XML (SOAP, SAML, RSS, SVG upload processing, Office documents, sitemap import). Search for XML parsers: PHP `simplexml_load_`, `DOMDocument->load`, `XMLReader`, `libxml_disable_entity_loader` (a no-op on PHP 8, not evidence), `LIBXML_NOENT`; Node `libxmljs`, `xml2js`, `fast-xml-parser`, `sax`, `xmldom`; Python `xml.etree`, `lxml.etree`, `xml.dom.minidom`, `xml.sax`, `defusedxml`. Check parser options for entity resolution and DTD loading (`resolve_entities=False`, `no_network=True`, `LIBXML_NONET`, no `LIBXML_NOENT`, `processEntities: false`).
**Implemented when:** The parser disables DTDs and external entity resolution (config key or flag cited at path:line), or `defusedxml` is used, or the language default is safe and no unsafe flag is set (PHP 8 with libxml 2.9+ and no `LIBXML_NOENT`).
**Not implemented when:** A parser is used with `LIBXML_NOENT`, `resolve_entities=True`, a DTD loader enabled, or the standard-library XML module parses untrusted input without `defusedxml`.

### V1.5.2 (Level 2, core)
**Requirement:** Verify that deserialization of untrusted data enforces safe input handling, such as using an allowlist of object types or restricting client-defined object types, to prevent deserialization attacks. Deserialization mechanisms that are explicitly defined as insecure must not be used with untrusted input.
**Where to look:** Search for deserialisation of data that may come from users, cookies, queues, caches or uploads: PHP `unserialize(` (look for `allowed_classes`), Laravel encrypted cookies are safe only with a protected `APP_KEY`; Node `node-serialize`, `js-yaml` `load` with unsafe schema, `vm`-based parsers; Python `pickle.load`, `pickle.loads`, `cPickle`, `shelve`, `marshal`, `yaml.load(` without `SafeLoader` (use `yaml.safe_load`), `jsonpickle.decode`. Check Java-style `ObjectInputStream` if present. Check session and cache drivers that store serialised objects and whether untrusted users can write there.
**Implemented when:** Untrusted data is parsed only as JSON or with safe loaders (`yaml.safe_load`, `unserialize($x, ['allowed_classes' => false])`, or an explicit class allowlist), or the search finds no such calls (cite the patterns grepped, directories covered and 0 hits). Otherwise cite each call site path:line.
**Not implemented when:** `unserialize`, `pickle.loads`, `yaml.load` without a safe loader, or similar is applied to request, cookie, upload or queue data written by untrusted parties, without an allowlist.


## V2 Validation and Business Logic

### V2.2.1 (Level 1, core)
**Requirement:** Verify that input is validated to enforce business or functional expectations for that input. This should either use positive validation against an allow list of values, patterns, and ranges, or be based on comparing the input to an expected structure and logical limits according to predefined rules. For L1, this can focus on input which is used to make specific business or security decisions. For L2 and up, this should apply to all input.
**Where to look:** Locate the input boundary: routes and controllers, API handlers, form handlers, CLI or queue consumers. Look for a validation layer: Laravel `FormRequest` classes, `$request->validate(`, `Validator::make`; Symfony `Assert\` constraints and `#[Assert`, Form types; Node `joi`, `zod`, `yup`, `ajv`, `express-validator`, `class-validator` with Nest `ValidationPipe`, `celebrate`, Fastify schemas; Python Django forms and serializers (`ModelForm`, DRF `Serializer`), `pydantic` models (FastAPI), `marshmallow`, WTForms. Check that rules are allowlists or typed ranges (enum, `in:`, `max:`, regex, `int` bounds), not only `required`. Sample the handlers that make security or business decisions: role changes, amounts, IDs, redirects, sort fields, file names.
**Implemented when:** Handlers that make security or business decisions (authentication, roles, amounts, record IDs, redirects, sort fields, file names) validate input against types, ranges, enums or patterns in a shared layer. Cite the validator class or schema path:line and which routes use it. At L2 all other handlers validate too.
**Not implemented when:** A handler that makes a security or business decision reads request data directly (`$_POST`, `req.body`, `request.args`) and uses it without checks, or rules exist only as `required`/`string`. `partial` is the case where all such decision handlers validate and other handlers (secondary instances, relevant at L2) do not; name them as path:line.

### V2.2.2 (Level 1, core)
**Requirement:** Verify that the application is designed to enforce input validation at a trusted service layer. While client-side validation improves usability and should be encouraged, it must not be relied upon as a security control.
**Where to look:** Find where client-side checks exist (HTML `required`, `pattern`, JS validation libraries) and confirm the same rule is enforced on the server. Search server entry points for the layer from V2.2.1 (FormRequest, DRF serializer, pydantic, zod, ValidationPipe) and look for handlers that trust the client: hidden form fields used for price, role or user ID, `req.body.isAdmin`, values accepted without re-check. Look for global middleware or pipes registering validation (`app.useGlobalPipes(new ValidationPipe`, `whitelist: true`).
**Implemented when:** Server-side handlers validate every field that the client also validates, in the trusted layer. Cite the server rule path:line next to the matching client rule if present.
**Not implemented when:** Validation exists only in front-end code, or the server accepts hidden or client-computed fields (prices, roles, IDs) as given.

### V2.4.1 (Level 2, core)
**Requirement:** Verify that anti-automation controls are in place to protect against excessive calls to application functions that could lead to data exfiltration, garbage-data creation, quota exhaustion, rate-limit breaches, denial-of-service, or overuse of costly resources.
**Where to look:** Look for rate limiting and quota code on expensive or abusable endpoints (login, password reset, signup, search, export, file upload, AI or paid-API calls, email sending). Laravel `throttle:` middleware and `RateLimiter::for` in `bootstrap/app.php` or `app/Providers/AppServiceProvider.php` (Laravel 11 and later; older versions use `app/Providers/RouteServiceProvider.php`); Symfony `rate_limiter` config and `framework.rate_limiter`; Node `express-rate-limit`, `rate-limiter-flexible`, `@nestjs/throttler` (`ThrottlerModule`), `@fastify/rate-limit`; Python Django `django-ratelimit`, DRF `DEFAULT_THROTTLE_CLASSES` and `DEFAULT_THROTTLE_RATES`, Flask-Limiter. Also check reverse-proxy config in the repo (`limit_req_zone` in nginx, Traefik `rateLimit`, Caddy `rate_limit`) and CAPTCHA integrations, plus pagination caps (`max` page size) and request body size limits.
**Implemented when:** A rate limit, quota or comparable control is configured and applied to the abusable endpoints. Cite the middleware or config key path:line and list the endpoints covered.
**Not implemented when:** No throttle, quota or proxy limit exists in the repo, or a limiter is defined but mounted on no route. Use `partial` only when mounted limits cover some abusable endpoints (for example login) and not others.


## V3 Web Frontend Security

### V3.3.1 (Level 1, core)
**Requirement:** Verify that cookies have the 'Secure' attribute set, and if the '\__Host-' prefix is not used for the cookie name, the '__Secure-' prefix must be used for the cookie name.
**Where to look:** Find cookie creation and cookie configuration. Frameworks: Laravel `config/session.php` keys `'secure'` and `'cookie'`, and `config/session.php` `'cookie'` name (look for `__Host-` or `__Secure-` prefix); Symfony `framework.yaml` `session.cookie_secure`; Express `res.cookie(`, `express-session` option `cookie.secure`, `cookie-session`, NestJS `session({ cookie: { secure: true } })`; Django `SESSION_COOKIE_SECURE`, `CSRF_COOKIE_SECURE`, `SESSION_COOKIE_NAME`; Flask `SESSION_COOKIE_SECURE`; PHP `setcookie(`, `session.cookie_secure` in `php.ini`. Search every `setcookie`, `res.cookie`, `set_cookie`, `Set-Cookie` in code. Environment-driven values (`env('SESSION_SECURE_COOKIE')`) count if the committed `.env.example` or deploy config sets true; cite it.
**Implemented when:** Every cookie the app sets has `Secure` true (explicitly, or via a framework setting cited by key) and uses the `__Host-` prefix, or the `__Secure-` prefix if `__Host-` is not possible. Cite config key path:line and the cookie name.
**Not implemented when:** The session cookie lacks `Secure`, or has `Secure` but no `__Host-` or `__Secure-` prefix. `partial` is the case where the session cookie is correct (attribute and prefix) and a secondary cookie set via `setcookie`/`res.cookie` lacks `Secure` or the prefix; name it as path:line.

### V3.3.2 (Level 2, core)
**Requirement:** Verify that each cookie's 'SameSite' attribute value is set according to the purpose of the cookie, to limit exposure to user interface redress attacks and browser-based request forgery attacks, commonly known as cross-site request forgery (CSRF).
**Where to look:** Find the same cookie settings as V3.3.1 and look for the `SameSite` attribute: Laravel `config/session.php` key `'same_site'`; Symfony `cookie_samesite`; Express `cookie: { sameSite: ` and `res.cookie(..., { sameSite`; Django `SESSION_COOKIE_SAMESITE`, `CSRF_COOKIE_SAMESITE`; Flask `SESSION_COOKIE_SAMESITE`; PHP `setcookie(` options array with `'samesite'`. Judge the value by the cookie's purpose: session and CSRF cookies `Lax` or `Strict`; cross-site embeds may need `None` with `Secure`.
**Implemented when:** Each cookie sets `SameSite` explicitly to a value that fits its purpose, or the framework default (Laravel `'same_site'` and Django `SESSION_COOKIE_SAMESITE` default to `Lax`; Express and PHP have no such default) is `Lax` and no override weakens it (cite the config key, for example `config/session.php` `'same_site' => 'lax'`). Cite the path:line.
**Not implemented when:** The session cookie has `SameSite=None` without a documented cross-site need, the attribute is unset on it with no framework default cited, or the config disables it. `partial` is the case where the session cookie is correct and a secondary hand-built cookie has an unfitting or unset `SameSite`.

### V3.3.4 (Level 2, core)
**Requirement:** Verify that if the value of a cookie is not meant to be accessible to client-side scripts (such as a session token), the cookie must have the 'HttpOnly' attribute set and the same value (e. g. session token) must only be transferred to the client via the 'Set-Cookie' header field.
**Where to look:** Find session, token and other sensitive cookies and check `HttpOnly`: Laravel `config/session.php` key `'http_only'`; Symfony `cookie_httponly`; Express `cookie: { httpOnly: true }`, `res.cookie(` options; Django `SESSION_COOKIE_HTTPONLY` (default true), `CSRF_COOKIE_HTTPONLY`; Flask `SESSION_COOKIE_HTTPONLY`; PHP `session.cookie_httponly` and `setcookie(` arguments. Then check that the same value is not also sent in a response body, URL, `localStorage` or `window.` variable: search front-end code for `localStorage.setItem('token'`, `sessionStorage`, `document.cookie` reads, and API responses that return a session or auth token.
**Implemented when:** Session and other script-inaccessible cookies set `HttpOnly` (cite the key or option), and the token is delivered only through `Set-Cookie` with no copy in the body, JS storage or URL.
**Not implemented when:** The session or auth cookie lacks `HttpOnly`, or its value is also returned in JSON or stored in `localStorage`. This includes apps that keep bearer tokens in JS storage on purpose; note the design. `partial` is the case where the session cookie is correct, the token travels only in `Set-Cookie`, and a secondary script-inaccessible cookie lacks `HttpOnly`.

### V3.4.1 (Level 1, core)
**Requirement:** Verify that a Strict-Transport-Security header field is included on all responses to enforce an HTTP Strict Transport Security (HSTS) policy. A maximum age of at least 1 year must be defined, and for L2 and up, the policy must apply to all subdomains as well.
**Where to look:** Search for the `Strict-Transport-Security` header in application code, middleware and proxy config files committed to the repo: Laravel custom middleware or `bepsvpt/secure-headers` config `hsts`; Symfony `nelmio/security-bundle` `forced_ssl`; Express `helmet()` (read the installed Helmet version from the lock file and the explicit `hsts.maxAge`; cite both), `res.setHeader('Strict-Transport-Security'`; Django `SECURE_HSTS_SECONDS`, `SECURE_HSTS_INCLUDE_SUBDOMAINS`; Flask-Talisman `strict_transport_security_max_age`; nginx `add_header Strict-Transport-Security`; Apache `Header always set Strict-Transport-Security`; Caddy `header`. A value of at least 31536000 seconds is required; L2 also needs `includeSubDomains`.
**Implemented when:** A header is set on all responses with `max-age` of 31536000 or more (and `includeSubDomains` for L2). Cite config key or file:line with the value.
**Not implemented when:** No HSTS header is set anywhere in the repo, `max-age` is below one year, or it is set only on some routes. If the header may be set by a CDN or proxy outside the repo, the status is still `not implemented`, with a note that infrastructure may set it.

### V3.4.2 (Level 1, core)
**Requirement:** Verify that the Cross-Origin Resource Sharing (CORS) Access-Control-Allow-Origin header field is a fixed value by the application, or if the Origin HTTP request header field value is used, it is validated against an allowlist of trusted origins. When 'Access-Control-Allow-Origin: *' needs to be used, verify that the response does not include any sensitive information.
**Where to look:** Search CORS configuration: Laravel `config/cors.php` keys `allowed_origins`, `allowed_origins_patterns`, `supports_credentials`; Symfony `nelmio_cors.yaml`; Express `cors(` options `origin`, `credentials`, manual `Access-Control-Allow-Origin` headers; NestJS `enableCors(`; Django `django-cors-headers` settings `CORS_ALLOW_ALL_ORIGINS`, `CORS_ALLOWED_ORIGINS`, `CORS_ALLOWED_ORIGIN_REGEXES`; Flask-CORS `origins`; proxy config `add_header Access-Control-Allow-Origin`. Look for code that reflects the request `Origin` header back (`$request->headers->get('Origin')` into the response, `origin: true`, `callback(null, origin)`).
**Implemented when:** No CORS header is set (same-origin only), or the origin is a fixed list of trusted origins, or the request Origin is checked against such an allowlist. Cite the config key path:line.
**Not implemented when:** Origin is reflected without an allowlist, `null` is allowed, or `*` is used together with credentials or on endpoints returning sensitive data. A confirmed unsafe site is `not implemented`, even if other sites are safe.

### V3.4.3 (Level 2, core)
**Requirement:** Verify that HTTP responses include a Content-Security-Policy response header field which defines directives to ensure the browser only loads and executes trusted content or resources, in order to limit execution of malicious JavaScript. As a minimum, a global policy must be used which includes the directives object-src 'none' and base-uri 'none' and defines either an allowlist or uses nonces or hashes. For an L3 application, a per-response policy with nonces or hashes must be defined.
**Where to look:** Search for the `Content-Security-Policy` header: Laravel `spatie/laravel-csp`, custom middleware; Symfony `nelmio/security-bundle` `csp`; Express `helmet.contentSecurityPolicy`, `res.setHeader('Content-Security-Policy'`; Django `django-csp` (version 4 uses the `CONTENT_SECURITY_POLICY` dict setting; older versions use `CSP_DEFAULT_SRC`, `CSP_OBJECT_SRC`, `CSP_BASE_URI`; read the installed version from the lock file); Flask-Talisman `content_security_policy`; nginx or Apache `add_header Content-Security-Policy`; `<meta http-equiv="Content-Security-Policy"` in templates (a meta tag does not support `frame-ancestors`). Read the directive list for `object-src 'none'`, `base-uri 'none'` (or `'self'` if the team accepts it, note this), and a script-source allowlist, nonces or hashes.
**Implemented when:** A global CSP header is sent on responses and contains `object-src 'none'`, `base-uri 'none'`, and a restricted `script-src` or `default-src` (allowlist, nonce or hash, no bare `'unsafe-inline'` or `*`). Cite the config key or file:line.
**Not implemented when:** No CSP exists, or it lacks `object-src` or `base-uri` (these two are the minimum), or `script-src` allows `'unsafe-inline'`, `'unsafe-eval'` or `*` without nonces. `partial` is the case where a global policy with both directives and a restricted `script-src` exists and there is a page-level or reporting gap, for example responses that bypass the middleware (static files, error pages) or a route that overrides the policy.

### V3.4.4 (Level 2, core)
**Requirement:** Verify that all HTTP responses contain an 'X-Content-Type-Options: nosniff' header field. This instructs browsers not to use content sniffing and MIME type guessing for the given response, and to require the response's Content-Type header field value to match the destination resource. For example, the response to a request for a style is only accepted if the response's Content-Type is 'text/css'. This also enables the use of the Cross-Origin Read Blocking (CORB) functionality by the browser.
**Where to look:** Search for `X-Content-Type-Options`: Laravel `bepsvpt/secure-headers` `x-content-type-options`, custom middleware; Symfony `nelmio/security-bundle` `content_type: { nosniff: true }`; Express `helmet()` (option `xContentTypeOptions`; read the installed version from the lock file and cite it), `res.setHeader('X-Content-Type-Options'`; Django `SECURE_CONTENT_TYPE_NOSNIFF` (default true) in `settings.py` with `SecurityMiddleware` listed in `MIDDLEWARE`; Flask-Talisman `content_type_options`; nginx or Apache `add_header X-Content-Type-Options nosniff`.
**Implemented when:** The header with value `nosniff` is added globally by middleware or server config, or by a framework default that is active (cite `MIDDLEWARE` entry or `helmet()` call path:line).
**Not implemented when:** No code or config sets the header, the middleware is not enabled, or it is only set on selected routes (static files served by the web server without it count as a gap).

### V3.4.6 (Level 2, core)
**Requirement:** Verify that the web application uses the frame-ancestors directive of the Content-Security-Policy header field for every HTTP response to ensure that it cannot be embedded by default and that embedding of specific resources is allowed only when necessary. Note that the X-Frame-Options header field, although supported by browsers, is obsolete and may not be relied upon.
**Where to look:** Search for `frame-ancestors` inside the CSP (same places as V3.4.3) and for legacy `X-Frame-Options`: Laravel secure-headers or middleware; Symfony `nelmio/security-bundle` `clickjacking`; Express `helmet.frameguard`, `helmet.contentSecurityPolicy` directive `frameAncestors`; Django `XFrameOptionsMiddleware`, `X_FRAME_OPTIONS`, `CSP_FRAME_ANCESTORS`; nginx or Apache `add_header`. Check that default is `'none'` or `'self'` and that embeds are allowed only per route when needed.
**Implemented when:** A CSP `frame-ancestors` directive (`'none'` or `'self'` by default) is sent on all responses. Cite the path:line. `X-Frame-Options` alone does not count.
**Not implemented when:** Only `X-Frame-Options` is set, `frame-ancestors` is missing, or it is `*` / an overly broad host list. Use `partial` when `frame-ancestors` is set on some responses only.

### V3.5.1 (Level 1, core)
**Requirement:** Verify that, if the application does not rely on the CORS preflight mechanism to prevent disallowed cross-origin requests to use sensitive functionality, these requests are validated to ensure they originate from the application itself. This may be done by using and validating anti-forgery tokens or requiring extra HTTP header fields that are not CORS-safelisted request-header fields. This is to defend against browser-based request forgery attacks, commonly known as cross-site request forgery (CSRF).
**Where to look:** Find how state-changing browser requests are authenticated. If the app uses cookie sessions: look for CSRF protection middleware: Laravel `VerifyCsrfToken` (check its `$except` list), `@csrf` in forms, `X-CSRF-TOKEN` headers; Symfony `csrf_protection` and `isCsrfTokenValid(`; Express `csurf`, `csrf-csrf`, `lusca`; NestJS `csurf`; Django `CsrfViewMiddleware` in `MIDDLEWARE` and `{% csrf_token %}`, `@csrf_exempt` usages; Flask-WTF `CSRFProtect`. If the app uses only bearer tokens in an `Authorization` header (not cookies) or requires a custom header with CORS preflight, cite that instead. Check SameSite settings from V3.3.2 as a supporting control, not a replacement.
**Implemented when:** State-changing routes that use cookie authentication verify an anti-forgery token or a non-safelisted custom header, with the middleware enabled globally and exemptions justified. Cite the middleware path:line and the exempt list. Pure bearer-token APIs satisfy it by design only with both: the search showing no cookie-based session (patterns such as `session`, `setcookie`, `res.cookie`, `cookie-parser`, directories covered, 0 hits) and the auth config path:line showing the `Authorization` header guard.
**Not implemented when:** CSRF middleware is absent or disabled, or login and state-changing forms post without a token (`@csrf_exempt`, `$except = ['*']` or a missing `{% csrf_token %}`/`@csrf`). `partial` is the case where those forms are protected and secondary instances (AJAX or JSON endpoints on cookie auth, webhooks) are exempt without justification; name them as path:line.

### V3.5.3 (Level 1, core)
**Requirement:** Verify that HTTP requests to sensitive functionality use appropriate HTTP methods such as POST, PUT, PATCH, or DELETE, and not methods defined by the HTTP specification as "safe" such as HEAD, OPTIONS, or GET. **Not implemented when:** A GET (or HEAD/OPTIONS) route performs a write, delete, logout, password or setting change. List each as path:line. A confirmed unsafe site is `not implemented`, even if other sites are safe.

### V5.2.2 (Level 1, conditional: uploads)
**Requirement:** Verify that when the application accepts a file, either on its own or within an archive such as a zip file, it checks if the file extension matches an expected file extension and validates that the contents correspond to the type represented by the extension. **Where to look:** Applies only if the app accepts uploads. At each upload handler look for extension and content checks: Laravel `mimes:`, `mimetypes:`, `image`, `File::types(`, `getMimeType()`/`guessExtension()`; Symfony `File` constraint `mimeTypes`; multer `fileFilter` with `file.mimetype` (client-provided, not enough alone), `file-type` package (magic bytes), `sharp` or `jimp` re-encoding; Python `python-magic`, `filetype`, `imghdr` (removed in Python 3.13), Pillow `Image.open().verify()` or re-save, Django `FileExtensionValidator`, `ImageField`. **Implemented when:** The extension is checked against an allowlist and the content is verified (magic bytes via `file-type`/`python-magic`/`finfo`, or re-encoding images). Cite the validator path:line.
**Not implemented when:** Only the client-sent MIME type or only the filename extension is checked, or nothing is. A confirmed unsafe site is `not implemented`, even if other sites are safe.

### V5.3.1 (Level 1, conditional: uploads)
**Requirement:** Verify that files uploaded or generated by untrusted input and stored in a public folder, are not executed as server-side program code when accessed directly with an HTTP request.
**Where to look:** Applies only if uploads are stored where the web server can serve them. **Not implemented when:** A user-supplied name or path is joined into a filesystem path without a check that the resolved path stays in the base directory, or user data reaches `include`/`require`/`readFile` paths. A confirmed unsafe site is `not implemented`, even if other sites are safe.

## V7 Session Management

### V7.2.1 (Level 1, core)
**Requirement:** Verify that the application performs all session token verification using a trusted, backend service.
**Where to look:** Find where the server decides who the user is on each request. Laravel: `auth` middleware, `config/auth.php` `guards`, `config/session.php` key `'driver'`; Sanctum or Passport guards. **Not implemented when:** The server trusts an identity or role value that the client can set (an unsigned cookie, a header, a localStorage value sent back) on the main authenticated routes, without a backend lookup or verification. `partial` is the case where the main routes use verified sessions and a secondary route (an API or WebSocket endpoint) reads identity from client input; name it as path:line.

### V7.2.3 (Level 1, core)
**Requirement:** Verify that if reference tokens are used to represent user sessions, they are unique and generated using a cryptographically secure pseudo-random number generator (CSPRNG) and possess at least 128 bits of entropy.
**Where to look:** Find which session token type is used and how IDs are made. Reference tokens from a framework session: Laravel `Illuminate\Session` (40 random characters), Django `SessionStore` (`get_random_string(32)`), `express-session` with a `genid` option (default uses `uid-safe`, 24 bytes). Hand-made IDs: search `session_id(`, `session_create_id`, `genid`, `Math.random`, `uniqid`, `md5(`, `time()` near session or token creation. Read the framework version in the lock file. For API tokens: Sanctum `HasApiTokens` (40 random characters), `crypto.randomBytes(`, `secrets.token_urlsafe(`.
**Implemented when:** Session or reference tokens are generated by the framework default or by a CSPRNG call yielding at least 16 random bytes. Cite the lock file line with the framework version; for a custom generator also cite the `genid` or generator path:line. If sessions are signed cookies or JWT only (no server-held reference token), the status is `n/a`; cite the config showing it (`SESSION_ENGINE` signed cookies, Laravel `'driver' => 'cookie'`).
**Not implemented when:** A custom generator for the session cookie or main API token uses a non-CSPRNG source or fewer than 128 bits (short IDs, sequential IDs, `md5(time())`, `uniqid`, `Math.random`). `partial` is the case where the session cookie is framework-generated and a secondary reference token (password-reset link, API key) is weak; name it.

### V7.2.4 (Level 1, core)
**Requirement:** Verify that the application generates a new session token on user authentication, including re-authentication, and terminates the current session token.
**Where to look:** Read the login success path. Laravel: `$request->session()->regenerate()` after `Auth::attempt` (Breeze `AuthenticatedSessionController@store`, Fortify does this itself; cite the file), `Auth::login`. Django: `login(request, user)` calls `cycle_key()`; custom code that sets `request.session['user_id']` directly bypasses it. Express: `req.session.regenerate(` before setting the user, Passport 0.6 or later regenerates in `req.login` (read the version from the lock file). Check re-authentication paths (sudo mode, `password.confirm`) and logout handlers that invalidate the old session.
**Implemented when:** The session ID changes at login and the old one is discarded. Cite the `regenerate()`/`login()` call path:line or the Passport version line.
**Not implemented when:** The main login handler sets session state without regenerating the ID, or reuses a pre-login ID (session fixation). `partial` is the case where the main login regenerates and a secondary login path (SSO callback, API cookie login, impersonation) does not; name it as path:line.

### V7.3.1 (Level 2, core)
**Requirement:** Verify that there is an inactivity timeout such that re-authentication is enforced according to risk analysis and documented security decisions.
**Where to look:** Find the idle timeout. Laravel: `config/session.php` key `'lifetime'` (minutes; the session is touched on each request, so it slides) and `'expire_on_close'`. Django: `SESSION_COOKIE_AGE` is an absolute expiry unless `SESSION_SAVE_EVERY_REQUEST = True`, which makes it slide. Express: `express-session` `cookie.maxAge` is absolute unless `rolling: true`; a store `ttl` alone is not an idle timeout. JWT sessions: short `exp` plus refresh does not count unless refresh requires recent activity. Search for a custom idle check (`last_activity`, `lastActivity`). Compare with any documented value in `SECURITY.md` or docs.
**Implemented when:** An inactivity timeout exists that slides with activity and is at most 24 hours. Cite the key and value (for example `config/session.php: 'lifetime' => 30`). A framework default counts only with the cited config file, key and installed version.
**Not implemented when:** No inactivity timeout exists: the session never expires, or the expiry is absolute only (Django `SESSION_COOKIE_AGE` without `SESSION_SAVE_EVERY_REQUEST`, Express `maxAge` without `rolling: true`). `partial` is the case where an inactivity timeout exists and is longer than 24 hours; state the value.

### V7.3.2 (Level 2, core)
**Requirement:** Verify that there is an absolute maximum session lifetime such that re-authentication is enforced according to risk analysis and documented security decisions.
**Where to look:** Find the maximum lifetime regardless of activity. Laravel: `config/session.php` `'lifetime'` slides on activity by default; an absolute limit needs custom middleware comparing a `login_at` value. Django: `SESSION_COOKIE_AGE` is absolute unless `SESSION_SAVE_EVERY_REQUEST = True`, in which case an absolute cap needs custom middleware comparing a stored login time. **Implemented when:** A hard cap exists that applies even to active sessions. Cite the config key and value or the middleware path:line.
**Not implemented when:** Only a sliding timeout exists and sessions or refresh tokens can be kept alive forever (`rolling: true` with no cap, a refresh token that never expires). `partial` is not used.

### V7.4.1 (Level 1, core)
**Requirement:** Verify that when session termination is triggered (such as logout or expiration), the application disallows any further use of the session. **Where to look:** Read the logout handler and expiry path. Django: `logout(request)` calls `flush()`; check `SESSION_ENGINE` signed cookies, where server-side invalidation is not possible. Express: `req.session.destroy(`, `req.logout(` (callback form in Passport 0.6 or later) and a store that deletes the record. Self-contained tokens: a denylist (`jti` table), per-user `token_version` or `iat` check, key rotation. Search for logout routes that only clear the cookie.
**Implemented when:** Logout and expiry destroy server-side session data, or self-contained tokens are rejected after logout via a denylist or per-user version check. Cite handler path:line and the store or denylist.
**Not implemented when:** The main web logout only deletes the client cookie or token and the old session ID or JWT still authenticates on the next request. `partial` is the case where the main web logout invalidates server-side and a secondary path (API token, mobile client) does not; name it as path:line.

### V7.4.3 (Level 2, core)
**Requirement:** Verify that the application gives the option to terminate all other active sessions after a successful change or removal of any authentication factor (including password change via reset or recovery and, if present, an MFA settings update).
**Where to look:** Find the session-termination option after credential changes. Laravel: `Auth::logoutOtherDevices($password)`, middleware `AuthenticateSession` (in `bootstrap/app.php` or `Kernel.php`), Jetstream/Breeze browser sessions page, Sanctum `tokens()->delete()`. Django: `update_session_auth_hash(request, user)` after password change, which invalidates other sessions, and a session list view. **Implemented when:** After a password change or reset (and MFA change if present), other sessions end or the user is offered to end them. Cite the call path:line.
**Not implemented when:** No code ends other sessions after a credential change, and no UI offers it. `partial` is the case where it happens for password change but not for password reset or MFA changes.

### V7.5.1 (Level 2, core)
**Requirement:** Verify that the application requires full re-authentication before allowing modifications to sensitive account attributes which may affect authentication such as email address, phone number, MFA configuration, or other information used in account recovery.
**Where to look:** Find the handlers that change email, phone, MFA settings or recovery data. Laravel: `password.confirm` middleware or `RequirePassword`, `config/auth.php` key `'password_timeout'`, Fortify `confirmPassword`; Django: custom `login_required` plus a recent-auth check (`session['reauth_at']`), `django-allauth` reauthentication; Express: handlers on `/email`, `/phone`, `/mfa` that call `bcrypt.compare(` or require a fresh login time. ## V9 Self-contained Tokens

### V9.1.1 (Level 1, conditional: jwt)
**Requirement:** Verify that self-contained tokens are validated using their digital signature or MAC to protect against tampering before accepting the token's contents.
**Where to look:** Find every place a token is parsed. First decide whether tokens are self-contained: Sanctum issues opaque tokens (a database lookup), so an app using only Sanctum has no self-contained tokens and the status is `n/a`. Passport verifies through League OAuth2 Server and `lcobucci/jwt`; cite the verifying call or the library version line. PHP: `firebase/php-jwt` `JWT::decode($jwt, new Key(`, `lcobucci/jwt` `Parser` plus `Validator` with `SignedWith`. Python: `jwt.decode(` (PyJWT) without `options={'verify_signature': False}`, `djangorestframework-simplejwt` `TokenBackend.decode(`, `authlib.jose`. Node: `jsonwebtoken.verify(` versus `jsonwebtoken.decode(` (decode does not verify), `jose` `jwtVerify(`. Search `verify_signature`, `ignoreSignature`, `complete: true`.
**Implemented when:** Every token whose claims are used for access decisions is passed through a verify call with a key or secret. Cite each verify call path:line and the library line in the manifest.
**Not implemented when:** A token's claims are used after `decode` without verification, or `verify_signature` is false on any path. A confirmed unverified token path is `not implemented`. `partial` only when verification is present everywhere and the secret is weak or hard-coded (cite the key location).

### V9.1.2 (Level 1, conditional: jwt)
**Requirement:** Verify that only algorithms on an allowlist can be used to create and verify self-contained tokens, for a given context. The allowlist must include the permitted algorithms, ideally only either symmetric or asymmetric algorithms, and must not include the 'None' algorithm. If both symmetric and asymmetric must be supported, additional controls will be needed to prevent key confusion.
**Where to look:** Read the verify calls and token config for the algorithm. PHP: `new Key($secret, 'HS256')` (a single algorithm per key), `lcobucci/jwt` `Signer\Hmac\Sha256`/`Rsa\Sha256`. Python: `jwt.decode(token, key, algorithms=['HS256'])` (the `algorithms` argument must be present), simplejwt `SIMPLE_JWT['ALGORITHM']` and `VERIFYING_KEY`. Node: `jsonwebtoken.verify(token, key, { algorithms: ['RS256'] })`, `jose` `jwtVerify(token, key, { algorithms: [`). Search `alg`, `algorithms`, `'none'`, `HS256` mixed with `RS256`, and keys loaded from the token header (`kid`, `jku`) without a fixed source.
**Implemented when:** Each verify call passes an explicit algorithm allowlist without `none`, covering either symmetric or asymmetric only. Cite each call path:line and the list.
**Not implemented when:** A primary verify call omits the allowlist, includes `none`, accepts both an HS and an RS algorithm for the same key, or takes the key from the token header (`kid`, `jku`). A confirmed unrestricted verify path is `not implemented`. `partial` is the case where the primary call is correct and a secondary verify call has no allowlist, or allowlists are present everywhere and exclude `none` but a list names both algorithm families (for example `['HS256','RS256']`). When key separation cannot be confirmed the status is `partial` and the reason must say "key separation unconfirmed".

### V9.2.1 (Level 1, conditional: jwt)
**Requirement:** Verify that, if a validity time span is present in the token data, the token and its content are accepted only if the verification time is within this validity time span. For example, for JWTs, the claims 'nbf' and 'exp' must be verified.
**Where to look:** Check expiry claims are issued and enforced. PHP: `JWT::decode` verifies `exp` and `nbf` itself (cite `firebase/php-jwt` version); `lcobucci/jwt` needs `StrictValidAt` or `LooseValidAt` constraints. Python: PyJWT verifies `exp` and `nbf` by default; check `options={'verify_exp': False}`; simplejwt `ACCESS_TOKEN_LIFETIME`. Node: `jsonwebtoken.verify` checks `exp`/`nbf` unless `ignoreExpiration: true`; `jose` `jwtVerify` checks them. Search `ignoreExpiration`, `verify_exp`, `leeway`, and the issuing code for `expiresIn`, `exp`.
**Implemented when:** The tokens carry `exp` (and `nbf` where used) and the primary verify call enforces them. Cite the verify call path:line and the option or default that enforces it, and for tokens the app issues the lifetime setting with its value.
**Not implemented when:** The primary verify call ignores `exp` or `nbf` (`ignoreExpiration: true`, `verify_exp: False`, neither `StrictValidAt` nor `LooseValidAt` configured in `lcobucci/jwt`), or the primary tokens are issued without `exp`. An app whose tokens never carry `exp` has no validity span to check, but the ASVS L1 intent is that tokens expire, so the status is `not implemented`. `partial` is the case where the primary path is correct and a secondary verify path skips the check; name it as path:line.

### V9.2.3 (Level 2, conditional: jwt)
**Requirement:** Verify that the service only accepts tokens which are intended for use with that service (audience). For JWTs, this can be achieved by validating the 'aud' claim against an allowlist defined in the service.
**Where to look:** Check audience validation at verification. PHP: `lcobucci/jwt` `PermittedFor`, `firebase/php-jwt` does not check `aud`, so look for manual `$decoded->aud` comparison. Python: `jwt.decode(..., audience='api')`, simplejwt `AUDIENCE`. Node: `jsonwebtoken.verify` option `audience:`, `jose` `jwtVerify` option `audience:`. Search `aud`, `audience`, `iss`, `issuer`. Check tokens from an IdP are not accepted for other services.
**Implemented when:** Verification requires an `aud` value from a fixed allowlist in configuration. Cite the option path:line and the configured value.
**Not implemented when:** The primary token verification path has no audience check although the claims are used for access. `partial` is the case where `aud` is checked on the main API and absent on a secondary verify call.


## V10 OAuth and OIDC

### V10.2.1 (Level 2, conditional: oauth-client)
**Requirement:** Verify that, if the code flow is used, the OAuth client has protection against browser-based request forgery attacks, commonly known as cross-site request forgery (CSRF), which trigger token requests, either by using proof key for code exchange (PKCE) functionality or checking the 'state' parameter that was sent in the authorization request.
**Where to look:** Find the authorization request and callback. Laravel: `laravel/socialite` (state is on by default; `->stateless()` disables it, so search for it), `league/oauth2-client` `getState()`. Django: `authlib` `authorize_redirect`, `social-auth-app-django` (`SOCIAL_AUTH_*`, state is on by default), `django-allauth`. Node: `passport-oauth2`/`passport-google-oauth20` `state: true`, `openid-client` v5 `generators.state()`/`generators.codeVerifier()` with `code_challenge_method: 'S256'`, v6 `randomState()`, `randomPKCECodeVerifier()`, `calculatePKCECodeChallenge()` and `authorizationCodeGrant(` options `expectedState`, `pkceCodeVerifier` (read the version from the lock file). Check the callback compares `state` to the session value or sends `code_verifier`.
**Implemented when:** The authorization request carries a random `state` that the callback verifies against the session, or PKCE (`code_challenge` with `S256`) is used. Cite the redirect and callback path:line, or the strategy option such as `state: true`.
**Not implemented when:** The callback accepts a code with no `state` check and no PKCE (`->stateless()` on a cookie-session login, `state: false`, no verification). A confirmed login callback without protection is `not implemented`. `partial` only when the main provider is protected and a secondary provider is not.
